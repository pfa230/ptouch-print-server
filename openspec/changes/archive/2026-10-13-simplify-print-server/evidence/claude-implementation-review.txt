I found one verified correctness defect in the implementation. It is medium severity and has a two-line fix. I found no material regressions in the cut lifecycle, failure cleanup and uncertain-output latch, USB selection, the CUPS decoder patch, or the default bridge. Two things remain unverified ordinary-CUPS cases that the tests skip, and some docs are stale and should be fixed before archive.

## Verified defects

**1. Medium: a size given only by name inside `media-col` is not treated as an explicit size. PNG then replaces it with the image-derived length.**
- **Where:** `src/filter_png.c:83-96` (`pt_explicit_length`) only looks at `media-col.media-size.y-dimension` and the top-level `media` keyword.
- **Trigger:** PAPPL accepts `media-col { media-size-name "om_12x50mm_12x50mm" }`. It validates the name against `media-supported` (`printer-ipp.c:2270-2294`), and `_papplMediaColImport` (`printer-support.c:551-559`) sets the 50 mm length from the name and prefers the name over x/y dimensions.
- **Consequence:** `pt_explicit_length` returns false, so `pt_set_page_length` overwrites the 50 mm with the image length (25.4 mm for 180 rows). This breaks "explicit geometry honored" for any IPP client that sends a size name rather than dimensions. CUPS sends dimensions, which is why your CUPS fixture passed. [verified by source path; not exercised by any test]
- **Same gap in the raster patch:** `patches/pappl-1.4.11-raster.patch:94-95` computes `explicit_width`/`explicit_length` from top-level `media` or `media-size` x/y only. So a contradictory size given by name is not rejected. This is less harmful because the raster page's own geometry still prints, but it misses the "contradictory explicit geometry fails visibly" requirement for this form.
- **Fix:** in both places, also treat `media-col.media-size-name` as explicit when `pwgMediaForPWG(name)` resolves with `length > 0`. Add one PNG case to `run_image`: `media-col` with only the size name should give 354 rows.

**2. Low: idle status polling can mark the printer offline while a job is printing.**
- **Where:** `src/driver.c:588-606`.
- **Trigger:** PAPPL decides whether to run the status callback while holding its lock, then releases the lock and calls it (`printer-ipp.c:1783-1789`, `printer-accessors.c:528-532`). If a job starts in that gap, `papplPrinterOpenDevice` returns NULL. The new code then sets OFFLINE, sets media to unconfirmed, and logs "present but cannot be opened or claimed". The old code cleared OFFLINE in this case.
- **Consequence:** clients can briefly see a false `offline` reason and a misleading error log while a healthy job prints. The next idle poll clears it, and no output is affected.
- **Fix:** in the NULL-open branch, return without publishing when `papplPrinterGetState(printer) == IPP_PSTATE_PROCESSING`. Keep OFFLINE for the genuinely unclaimable case.

## Assumptions and gaps (need one check each)

- **[assumption] Multi-copy PDF through CUPS may be rejected.** Without a `document-format`, PAPPL advertises `copies-supported 1-999` (`printer-ipp.c:77-84`). If the generated CUPS queue passes copies=N to the backend for a PDF it converts to PWG raster, the patched validation rejects copies≠1. CUPS's default error policy may then stop the queue. `check-cups.py` only sends PDFs with one copy. **Check:** `lp -n 2` on the two-label PDF through the driverless queue. If it fails, decide the behavior explicitly; quietly printing once would be worse.
- **[assumption] Custom lengths through CUPS may be rejected for 6/9/12/24 mm.** CUPS normally takes a single printer-wide minimum margin for custom sizes. Your published minimums are 53/57 centimm. For 12 mm that gives a left offset of 3 px, below `g.left_px` = 4, so `r_startpage` would reject it. This would be truthful but surprising. **Check:** `lp -o media=Custom.12x40mm label.png`.
- **[verified] JPEG geometry is not refreshed first.** PAPPL's JPEG filter builds print options before `r_startjob` refreshes the tape. After an offline start or an unpolled cassette change, a JPEG fails visibly with a width-mismatch error and sends no output. This behavior is not new, and the spec scenario only promises it for PNG. No action is needed beyond being aware of it.

## Your two diagnostic nuances

- **`job-impressions-completed=1` on the aborted incomplete job:** this is not a contract defect. PAPPL counts the page as soon as it starts, before any rows are decoded or any callback runs (`job-process.c:645`). It records input pages, not proven physical output. The authoritative signals are correct: job aborted, a format-error reason, no FF/EJECT, and the latch reporting `other` with the recovery log. No change is needed; at most, note this meaning in the README.
- **10 s client timeout on the streamed raster job:** this was a test-client setting, not a product defect. PAPPL replies to a streamed raster Print-Job only after end-job, so the reply time equals the physical print time. CUPS's backend waited through your multi-label PDF runs. Generic clients with short timeouts could report a failure for a job that actually completed. That is how PAPPL streaming works and predates this change, and nothing here replays the job.

## Areas reviewed with no material issue

- **Deferred FF / final EJECT:** a label's print command waits until the next label passes validation or end-job succeeds. A failed next-label validation leaves the run uncertain rather than finalizing it.
- **Precut and continuation:** ESC @ is sent only for a known closed run, and precut happens only on the first label of each batch.
- **Cleanup:** the run is marked uncertain before any setup is sent; cleanup is idempotent; a rejected or canceled follower that sent nothing leaves the previous run intact.
- **Finishings resolution:** enum handling covers 60+63, 63+60, none alongside other values, and 11/60 as equivalents; it is consistent with the patch's `_papplTrimSelection`.
- **Dependency patches:** the CUPS patch is correct; errors are cleared when a stream opens (`raster-stream.c:450`), so a failure does not carry over to the next job on the same thread. PAPPL regenerates its driver attributes only in `SetDriverData`, so the bridge's replacements survive `SetReadyMedia`. The version-pin guards fail closed.

## Avoidable complexity

- **[design preference] Duplicate lifecycle in the probe:** the cut probe's `batch` sequence (`tests/cut_probe.c` `run_batch`) is a second implementation of the lifecycle the driver now runs and that passed physical testing. After archive, consider trimming it to the historical diagnostic sequences, so the probe and driver cannot drift apart.
- **Redundant CI step:** the first workflow step (`target: build`) repeats the CTest run that the runtime image build already does through the same stage. It is harmless but redundant.
- **Accepted trade-off, not a defect:** rebuilding CUPS and pinning its version is the largest maintenance cost. Every Debian CUPS security release will turn CI red until the patch is refreshed, which blocks unrelated publishes in the meantime. You approved this.

Nothing else I found adds substantial unnecessary machinery for your stated goals.
