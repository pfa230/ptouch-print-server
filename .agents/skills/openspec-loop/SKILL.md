# Supervise an openspec-loop run

The loop runs a committed OpenSpec change unattended. Supervision uses only these five commands:

- `loop run <change>` starts a run and advances it in the foreground. It prints a progress line, prefixed with the time, as each step starts and ends, then a report. It exits 0 when the run completes, 1 when it stops, and 2 when it refuses to start.
- `loop step <change>` enrolls a new run or continues an existing one through the first successful pending-stage completion, including its internal cycles and recovery handoffs. It exits 0 when it returns control between stages or completes the whole run, 1 when it stops and 2 when it refuses. It shares the existing state, preparation, lock, transcripts and configured attempt budgets; it accepts no options.
- `loop status <change>` shows the run's state, branch, stages and locations.
- `loop stop <change>` ends the current step at once; the active advancement then prints its stop report.
- `loop run`, `loop step` and `loop resume` accept four agent aliases after the change name, in role order: proposal reviewer, plan reviser, implementer, implementation reviewer. When the user names four agents, pass them in that order, for example `loop run <change> claude codex muse deepseek`. The loop writes them to the run worktree's `openspec/loop.local.yaml`, so later commands invoked from that worktree keep them.
- `loop resume <change>` continues a run that is between stages, stopped or interrupted, with a fresh attempt budget; `loop resume <change> --attempts <n>` sets that budget, and `--implement` sends the run back to the implementer, which implements the plan as it stands; proposal review stays as it is, so an approved plan is not reviewed again. It advances in the foreground like `loop run`, with the same output and exit statuses.

## Rules

- Run every `loop` command outside the supervising session's sandbox. The loop writes the repository's Git directory, which sandboxes make read-only, and it starts its own workers. In a Codex session, request escalated permissions for each `loop` command.
- Relay each progress line to the user as it appears, in order and unchanged. Do not batch them until the run ends.
- When the command exits, show the user the report unchanged, in a code block. On a stop, identify the reported stage and transcript paths, then diagnose the stop as described under Diagnosing a stop before discussing recovery. Relaying the report and explaining the cause are separate obligations; a stage, agent alias and exit status are not a causal diagnosis.
- Run `loop stop` only when the user asks, and leave a stop the user requested stopped. A successful stage boundary is an inspection point: show its report unchanged, identify what can run next and wait for the user without diagnosing a failure or automatically advancing. After diagnosing any other stop, apply its recovery and resume without waiting for the user, unless the stop needs the user, as described under Diagnosing a stop.
- Change nothing to investigate a stop: do not edit the run's state, worktree or transcripts, and do not commit, resume or rerun anything to test a theory. Diagnose by reading only, as described under Diagnosing a stop. Change the run only after the diagnosis, to apply a recovery.

## Watching a run in Claude Code

1. Start the command with Bash and `run_in_background: true`, redirecting its output to a log file: `loop run <change> > <log> 2>&1`. Use `loop resume <change>` or `loop step <change>` the same way.
2. Start a Monitor on `tail -n +1 -f <log>` with the longest timeout. Each new line arrives as a notification. Relay each progress line, which starts with the time, and keep count of the lines relayed. The first line that does not start with the time ends the relay: relay neither it nor any line after it, because Monitor events drop each line's leading whitespace, and step 3 shows the rest from the log. If the monitor expires while the run continues, re-arm it with `tail -n +<count + 1> -f <log>`, so no line is skipped or repeated.
3. When Bash reports that the background command exited, stop the monitor, read the log with Bash from the first line not yet relayed to the end, and show the user all of those lines unchanged, in a code block, with the exit status.

## Watching a run in Codex

Verified with Codex CLI 0.160.0. Start the command with `exec_command` and a short `yield_time_ms` such as 1000. While the command runs, the call returns the lines printed so far and a session id. Poll that session with `write_stdin`, passing empty `chars`, and relay the new lines from each poll. The poll that returns the exit status also carries the report.

## Supervising several runs

When the user names several changes, run them at once, each as an ordinary run in its own worktree. Only the named changes run.

1. **Check the branch.** Compare `git branch --show-current` in the invoking checkout with the configured `defaultBranch`, merged as under Diagnosing a stop. On any other branch, every run would share the invoking worktree: name that branch and the default branch, and start no run.
2. **Check dependencies.** Read each named change's `proposal.md`, `design.md` and `tasks.md` under `openspec/changes/<change>/` for work it needs, such as a requirement, file, command or change it names. Check whether the default branch holds that work, from `openspec/specs/`, the archived changes under `openspec/changes/archive/` and the default branch's files. Another named change counts as unlanded, because parallel runs do not see each other's work. Check only direct dependencies; do not trace further or order the changes. For each change that needs unlanded work, name the missing work and the evidence by file and line, propose dropping the change, and wait for the user's list of changes to run. When nothing is flagged, start at once.
3. **Start every run.** Start `loop run <change>` for each change to run without waiting for any to end.
4. **Relay each run's progress.** Forward each progress line as `<change>: <line>`; the label is the only change to the line.
   - In Claude Code, give each run its own background Bash command, log, Monitor and relayed-line count, and watch each as under Watching a run in Claude Code. Re-arm an expired monitor from that run's own count.
   - In Codex, give each run its own `exec_command` session and poll the sessions in turn with `write_stdin`.
5. **Handle each run as it ends.** Show its report unchanged and handle it as a single run: diagnose a stop, and resume only after the user agrees. Meanwhile keep relaying the other runs. Watch a resumed run alongside the rest.
6. **Summarize.** When every run has ended, list each change you ran, in the order the user named them, one per line with its outcome as its last report states it: `completed`, `stopped at <stage>` or `refused`. Do not repeat the reports or diagnoses.

## Stopping and resuming

To stop, run `loop stop <change>` from any checkout of the repository; the watched advancement prints the stop report and exits 1. To continue, start `loop resume <change>` and watch it the same way. For one successful stage at a time, use `loop step <change>` and watch it the same way; the report names the stage completed and what can run next. Returning between stages is different from a stopped run and from whole-run completion. After resolving a stop, `step` follows the same recovery as `resume`, within its single-stage limit. If `loop status` shows the run as interrupted, the process advancing it died; `loop resume` takes the run over and redoes the interrupted step.

## Diagnosing a stop

The loop reports observed outcomes without investigating their cause. The supervising session diagnoses stops and recovers from them. Use only reads: the report, `loop status`, `cat`, `tail` and `jq` on the files under the run directory, `git status --short`, `git log` and `git diff` in the run's worktree, and `cat` on the invoking checkout's `openspec/loop.yaml` and `openspec/loop.local.yaml` and the main checkout's `openspec/loop.local.yaml`. For a decision stop, also read the change's planning artifacts under `openspec/changes/<change>/` in the run's worktree. When needed to distinguish a harness failure from an adapter's reply rejection, also use `command -v`, `readlink` and filesystem reads of the invoked adapter and its directly relevant helper. Inspect only the execution and reply-handling path needed to explain the error. The report names the worktree, the run directory and the transcripts directory.

Permitted commands for locating the main checkout include `git rev-parse --absolute-git-dir`, `git rev-parse --path-format=absolute --git-common-dir` and `git worktree list --porcelain -z` in the invoking checkout. When the Git directories match, that checkout is the main checkout. Otherwise, use the first NUL-delimited worktree record; a `bare` record means there is no main checkout. Verification may use `git rev-parse --show-toplevel` and the common-directory command in the reported checkout to check that its root matches the record and it belongs to the same clone. If Git does not identify an accessible working tree, report the location refusal; do not search for another root or change Git configuration. This includes linked worktrees with separated metadata when Git reports the metadata directory instead of the main checkout. Direct invocation from the main checkout with separated metadata works.

Configuration is merged from invoking committed, main local, then distinct invoking local files, and is reread on each run, resume or step. Local files are optional; a bare clone has only the invoking files. `defaultBranch`, `worktrees`, `checks` and `delivery` replace whole settings; `agents`, `roles` and `attempts` replace individual entries. Relative agent commands and worktrees paths refer to the invoking checkout, regardless of which file defines them.

1. **Classify the stop from the report's cause.** A stop by the user needs no diagnosis. A decision stop is answered as described below. A stop at integration or delivery for a dirty checkout, unpushed or diverged commits, or a rejected push carries its own recovery: explain it and hand it to the user. Diagnose the rest as an execution failure or as exhausted attempts.
2. **An execution failure.** Read the end of the transcript the cause names, the reply file if there is one, and the usage on the step's end line. For a worker's failure, also read the entry under `agents` for the alias the cause names: use the invoking local file when it defines that alias, otherwise the main local file when it defines it, otherwise the invoking committed file. Check the effective command's arguments, such as the model, against the error.
   - Identify the specific failed operation and quote the evidence establishing it, such as an authentication failure, a quota or rate limit (`401`, `402`, `429`), a network error, a permission the harness denied, a turn limit, a missing command, or reply rejection. Trace which process produced the reported failure; the wrapper's nonzero exit does not establish that its child failed.
   - If the transcript and command do not establish that distinction, locate and read the invoked adapter and its relevant helper. Inspect a script named in an interpreter's arguments, not just the interpreter. Relative commands and script paths refer to the invoking checkout. Name the inspected path; repository source may differ from the installed adapter used by the run. If the relevant code or its identity at the time of failure is unavailable, state that limit rather than applying current source behavior to an unverified invocation. Do not install, rebuild or execute the adapter or harness to investigate.
   - For example, cut-pass prose followed by JSON can make parsing the entire final-message text fail. If the invoked helper returns only after child exit 0 and parsing happens after that return, explain the causal chain: the child succeeded, the adapter rejected its final text, and the adapter exited before writing a reply. Merely noticing prose before JSON does not complete that explanation, and parsing rejection does not establish why the model ignored its formatting instruction. Recover with a schema-conforming final reply while preserving strict validation; an output-contract change needs its own proposal.
   - Establish the work left behind with `git status --short`, the existing history/diffs and run records: what is committed, what remains uncommitted, and which required checks and reviews completed or remain pending. Checks recorded inside a worker transcript are not proof that the loop ran its own checks or review. A failed final reply does not imply that implementation edits were lost or fully reviewed. If a part of that state cannot be established, name the missing evidence.
   - Say what the evidence does not show. When nothing in the report, the transcript or the reply names an error, such as a transcript that ends without one, an empty transcript or a step killed by a signal, the cause is open: say so instead of guessing. Missing usage alone does not make an explicit error uncertain.
   - A failed `git` or `gh` command quotes its output in the cause. A refused `openspec archive` names only its transcript, which holds OpenSpec's explanation: read it. An execution failure of the loop itself has no transcript, and its cause is all the evidence there is.
3. **Exhausted attempts.** List the run's `*.verdict.json` and `*.findings.json` files in the transcripts directory in step order, and compare their findings from attempt to attempt:
   - The same finding repeats: the implementer or plan reviser does not address it, or cannot within the plan.
   - The findings change every attempt: the reviewer's demands move, or each fix breaks something new.
   - The same check failure repeats unchanged: it may fail on the base too, and the implementer must not repair what the change did not break.

   Then look at what each attempt changed. Each implementation review record names the `commit` it reviewed: `git diff` consecutive ones in the worktree. For proposal review, diff the plan between the `<change>: revise plan` commits that `git log` shows on the run's branch.
4. **Present and recover.** Give the likely cause with the files and lines that support it and what the evidence leaves open. For an execution failure, include the failed operation and the work and validation left behind. Then state the recovery and apply it in the same turn, without waiting for the user. The recoveries are edits to the change's planning artifacts in the run's worktree, committed there on the run's branch with `git commit`, and the resume commands: `loop resume <change>`, `loop resume <change> --attempts <n>` after exhausted attempts, and `loop resume <change> --implement` after a plan edit to a run whose implementation is complete, which has the implementer implement the edited plan; a plain resume would continue where the run stopped. `--implement` is refused once the change is archived.

   Hand the stop to the user instead, with the diagnosis and the action the user must take, and do not resume, when no recovery addresses the cause without a decision that neither the user's instructions, the source issue, the plan nor the repository's rules settle. Fixing the environment, credentials, quota or billing, the main checkout or the remote, discarding the run as the README describes, and changing a decision the design records all need the user. Also hand over a stop that repeats a cause you already recovered from in this session, with both diagnoses.

## Answering a decision stop

When the report's cause says a review needs decisions the plan does not record, answer each question that the user's instructions, the source issue, the plan or the repository's rules settle, and name the source of each answer. When every question is settled, record the answers and resume as below, without waiting for the user. Otherwise show the report unchanged, then hand the open questions to the user in your own message, outside tool output and the report's code block, along with the answers you settled and their sources. The user must be able to answer from that message alone; pointing to "the questions above" or reminding the user that only they can decide is not a handoff.

1. **List every open question.** Number the questions and quote each exactly as the report lists it, all together in one message.
2. **Explain each one.** Under each question, say in plain language what it decides, the relevant choices and the practical tradeoff between them.
3. **Recommend.** Give a recommended answer with its reason, grounded in the change's planning artifacts and the review findings. When they cannot support a recommendation, say what evidence is missing instead of inventing a preference.
4. **Ask for a concise reply.** For example: `Reply with your choices for 1 and 2, or say "use both recommendations".`

A recommendation is advice, not a decision. Keep the run stopped and record nothing until the user answers every open question or explicitly approves the recommendations. The user's answers authorize recording, committing and resuming; do not ask for that separately. To record, write each answer into the change's `design.md` in the run's worktree that the report's recovery names, and commit it there on the run's branch with `git commit`. Then resume with `loop resume <change>` and watch the run as before. The resumed run reviews the plan again.
